# ADR-0005：部署脚本通过 `--db-info` 直接读取数据库状态

- 状态：已接受
- 日期：2026-10-25

## 背景

部署脚本需要在**更新前后**判断数据库的结构版本（`schema_version`）与行数，用来决定：

1. 更新是否真的推进了数据库结构（是否需要"先恢复快照再回滚"）；
2. 回滚之后数据是否完好。

最初的实现通过宿主机访问 `http://127.0.0.1:<端口>/api/v1/version` 获取结构版本。这带来两个
无法回避的问题：

- **NPM 共享网络模式不发布宿主机端口**，HTTP 请求根本不可达，检测必然失败；
- **应用可能已经无法启动**（更新失败、迁移失败、容器退出），此时 HTTP 也不可用，而回滚
  判断恰恰必须在这时做出。

结果就是：在 NPM 模式或应用已停止时，脚本**无法可靠判断**数据库是否已升级，只能盲目启动
旧镜像，存在用旧代码打开新结构数据库的风险。

## 决策

在应用二进制中新增一个部署辅助模式：

```bash
xiaowork-nav --db-info [--db /data/app.db]
```

它**直接打开数据库文件**并以只读方式（只执行 `SELECT`）输出：

```text
db_path=/data/app.db
exists=true
schema_version=2
categories=10
bookmarks=110
uploads=31
```

部署脚本通过 `docker run --rm -v <数据目录>:/data <镜像> --db-info --db /data/app.db`
调用它。实现上：

- `store.OpenForInspection`：用于只读检查的打开方式（只发 SELECT）；
- `migrations.ReadVersion`：不写库、`schema_migrations` 不存在时返回 0；
- `scripts/lib.sh` 的 `db_info` / `db_field` / `schema_version` 负责调用与解析。

配套的判定策略：当结构版本**变大**、**无法读取**或**更新前版本未知**时，一律**先用更新前
快照恢复数据**，再切回旧镜像。

## 理由

- **与部署形态无关**：只依赖数据目录的挂载与镜像本身，独立模式与 NPM 模式行为完全一致。
- **与应用状态无关**：容器停止、启动失败、迁移失败时依然可读。
- **不需要暴露任何端口**：满足"不得为了检测而把 NPM 模式端口暴露公网"的约束。
- **无额外依赖**：不需要 `jq`（`key=value` 便于 shell 解析），不需要挂载 Docker Socket，
  不需要额外的辅助容器。
- **只读、可安全调用**：不会建表、不会写入，可在应用仍持有数据库时调用。

## 影响

- 结构版本检测在**所有** Compose 模式下行为一致；NPM 模式的回滚从"不可判断"变为"可判断"。
- 无法读取结构版本时按"兼容性未知"处理（保守回滚），这是**有意的安全取舍**。
- 部署脚本对镜像有一个隐含要求：目标镜像必须包含 `--db-info`。更新流程总是先拉取镜像，
  因此正常情况下满足；`restore.sh` 在镜像缺失时只会跳过结构版本日志，不影响恢复。
- 该模式是**部署辅助入口**，不属于公开 API，不进入 OpenAPI 契约。

## 备选方案

| 方案 | 未采用的原因 |
| --- | --- |
| 保留 HTTP 查询 | NPM 模式不可达；应用停止时不可用 |
| 用 `sqlite3` CLI 读库 | 运行镜像（Alpine 精简镜像）不含 `sqlite3`，需额外安装或额外容器 |
| 挂载 `docker.sock` 让脚本/应用直接查询容器 | 使应用接近拥有宿主 Docker 管理权限，安全风险不可接受 |
| 让脚本解析数据库二进制格式 | 脆弱且与实现强耦合 |
| 依赖宿主机 `127.0.0.1` 端口（现状） | 正是本次要修复的缺陷 |
