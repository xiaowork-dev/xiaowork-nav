## 4. 实现的具体功能

### 4.1 首次部署数据目录权限修复（需求 6.4）

线上曾出现 `mkdir /data/uploads: permission denied`。根因：数据目录由宿主机账号（如 root）创建，
而容器以 `uid=100` 运行，绑定挂载的属主与容器用户不一致。

修复策略（**不使用 777，也不长期以 root 运行**）：

1. `deploy/compose*.yaml` 显式声明 `user: "${XN_UID:-100}:${XN_GID:-101}"`，容器始终非 root；
2. `scripts/install.sh` 在启动前调用 `ensure_data_dirs`：
   - 创建 `<data>`、`<data>/uploads`、`<data>/backups`；
   - 目录属主已是容器用户 → 不做任何改动；
   - 以 root 运行（或可用 `sudo -n`）→ `chown -R <uid>:<gid>`；
   - 无法 chown 且目录**为空**（全新安装）→ 自动把 `XN_UID`/`XN_GID` 设为当前账号，
     使容器与宿主机属主一致；
   - 无法 chown 且目录**已有数据** → **不改动配置**，只打印可复制的修复命令
     （避免破坏一个本来可用的部署）；
3. `deploy/docker-entrypoint.sh` 在启动应用前对数据目录做写入探测，失败时打印
   三条可复制执行的修复方案并**快速失败**，而不是启动成功后在保存图标时才报错。

## 12. 生产升级指令（**需用户确认后再执行**）

```bash
ssh <user>@<server>
cd /opt/xiaowork-nav

# 1) 先备份（可选但强烈建议）
./scripts/backup.sh

# 2) 拉取仓库最新代码（含新的部署脚本）
git pull --ff-only

# 3) 一键升级到 v2.1.0（自动快照 → 切换 → 健康检查 → 失败自动回滚）
./scripts/update.sh v2.1.0

# 4) 核验
curl -fsS http://127.0.0.1:<port>/api/v1/version    # 期望 version=v2.1.0, schema_version=3
docker inspect -f '{{.State.Health.Status}}' xiaowork-nav   # healthy
```

升级说明：

- 数据库结构版本 **2 → 3**（只增列、带默认值）；升级前会自动生成一致性快照。
- **降级需要恢复快照**（旧镜像无法读取新结构），命令：
  `./scripts/restore.sh <pre-update 快照> --version v2.0.1`。
- 若启动时报数据目录不可写，按提示执行 `sudo chown -R 100:101 /opt/xiaowork-nav/data`
  （或在 `.env` 中把 `XN_UID`/`XN_GID` 设为该目录属主），**不要使用 `chmod 777`**。
- 升级不会删除或覆盖任何数据；手动设置的图标不会被自动图标流程覆盖。

**本次开发未对生产服务器做任何操作。**
